# Рефакторинг и оптимизация клиента FanPay

Этот план описывает процесс разделения кода `fanpay_client.py` путём вынесения всех вспомогательных функций парсинга HTML, разбора форм и извлечения данных через BeautifulSoup во вспомогательный модуль `fanpay_parsers.py` в той же директории.

---

## 1. Текущие проблемы monolithic файла `fanpay_client.py`
1. **Слишком большой размер:** Файл содержит почти 1900 строк кода.
2. **Смешение зон ответственности (Violation of SoC):** В одном классе смешаны сетевые запросы (HTTP/асинхронность) и низкоуровневый парсинг HTML-элементов (селекторы, регулярные выражения, BeautifulSoup).
3. **Сложность поддержки:** Любое изменение верстки FunPay требует редактирования огромного основного файла клиента, что увеличивает риск случайно сломать сетевую логику.

---

## 2. Предлагаемая архитектура после рефакторинга

Мы создадим вспомогательный утилитный файл `@/backend/app/services/fanpay_parsers.py`, в который перенесём все чистые синхронные функции парсинга HTML. Сам клиент `FanpayClient` будет импортировать эти функции и заниматься исключительно асинхронными сетевыми запросами, управлением куками, прокси и повтором запросов (Retries).

### Содержимое `@/backend/app/services/fanpay_parsers.py`:
1. `extract_csrf_token(html: str) -> Optional[str]`: Извлечение токена CSRF.
2. `parse_profile_stats(html: str) -> Dict[str, Any]`: Разбор профиля (баланс, имя, рейтинг).
3. `parse_active_lots_list(html: str) -> List[Dict[str, Any]]`: Разбор лотов со страницы публичного профиля.
4. `parse_paid_orders_list(html: str) -> List[Dict[str, Any]]`: Разбор списка оплаченных заказов.
5. `parse_chat_node_id_and_history(html: str) -> Tuple[Optional[str], List[Tuple[str, str]]]`: Извлечение ID ноды чата и истории сообщений из страницы заказа.
6. `parse_dialogs_list(html: str) -> List[Dict[str, Any]]`: Разбор списка диалогов со страницы `/chat/`.
7. `parse_chat_messages_history(html: str) -> List[Dict[str, Any]]`: Разбор сообщений внутри чата.
8. `parse_lot_edit_form_details(html: str) -> Dict[str, Any]`: Разбор формы редактирования лота (цена, количество, скрытые поля).
9. `parse_lot_creation_form_details(html: str) -> Dict[str, Any]`: Разбор полей формы создания нового предложения.
10. `parse_all_categories_list(html: str) -> List[Dict[str, Any]]`: Разбор каталога всех игр и подразделов.

---

## 3. Пошаговый план реализации (Step-by-Step)

### Шаг 1: Создание файла `@/backend/app/services/fanpay_parsers.py`
* Создать новый файл, перенести туда BeautifulSoup парсеры и импортировать нужные библиотеки (`BeautifulSoup`, `re`, `json`, `logging`, `typing`).
* Все методы переделать в синхронные функции, принимающие `html: str` (и другие необходимые параметры) и возвращающие чистые структуры данных (словари, списки).

### Шаг 2: Рефакторинг `@/backend/app/services/fanpay_client.py`
* Удалить все BeautifulSoup конструкции и регулярные выражения из тела класса `FanpayClient`.
* Импортировать все утилиты из `fanpay_parsers.py`.
* Заменить длинный код парсинга внутри методов клиента на лаконичные вызовы функций парсера. Например, в `get_paid_orders`:
  ```python
  response = await client.get("https://funpay.com/orders/trade")
  return parse_paid_orders_list(response.text)
  ```

### Шаг 3: Проверка корректности (Тестирование)
* Запустить байт-компиляцию для проверки синтаксиса обоих файлов.
* Убедиться в отсутствии ошибок импорта в `@/backend/app/services/scheduler.py` и API-эндпоинтах.

---

## 4. Ожидаемые преимущества:
* **Сокращение кода:** Размер `fanpay_client.py` уменьшится примерно в 2.5 раза (с 1900 до ~600-700 строк)!
* **Читаемость:** Сетевая логика клиента станет кристально прозрачной.
* **Изолированность:** Если FunPay обновит дизайн, правки будут вноситься только в изолированные функции парсинга в `fanpay_parsers.py`, без затрагивания логики отправки запросов.
